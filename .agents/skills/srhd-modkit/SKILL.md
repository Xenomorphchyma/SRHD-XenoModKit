# SRHD ModKit

Использовать SRHD ModKit как основной программный интерфейс к модам Space Rangers HD. Работать через CLI или Python API без GUI.

## Найти корень ModKit

1. Найти корень репозитория, содержащий `srhd.py`, `pyproject.toml` и каталог `srhd_modkit`. Обозначать его как `<MODKIT_ROOT>`.
2. Если этот скилл загружен прямо из репозитория, `<MODKIT_ROOT>` находится на три уровня выше `SKILL.md`: `.agents/skills/srhd-modkit/../../..`.
3. Выполнить `python -B srhd.py --version` из `<MODKIT_ROOT>`. Ожидать `SRHD ModKit 0.10.0` или новее.
4. При другой версии сначала прочитать локальные `README_RU.md`, `AUDIT_RU.md` и вывод `python -B srhd.py --help`; не предполагать наличие `script decompile`.
5. Если корень найти нельзя, запросить путь к клону ModKit. Не использовать каталог установленной игры вместо инструментария.
6. Для точного синтаксиса читать [references/commands.md](references/commands.md).

## Выбирать workflow по задаче

- Для существующего мода без TOML начинать с `project init`, затем просмотреть предупреждения и `project plan`. Если найден `srhd-modkit.toml`, для обычной сборки предпочитать `project build`, перед выкладкой `project deploy --dry-run`, а для единого выпуска папки/ZIP/manifest/audit/provenance — `project publish`. Машинные пути брать только из непубликуемого `srhd-modkit.local.toml`. Перед ручной очисткой использовать `project doctor` и dry-run `project clean`; `--apply`, `--build` и `--cache` добавлять осознанно. Project workflow точно заменяет одну папку варианта и автоматически ограничивает кэш; `.srhd-build`/`.srhd-cache` не копировать в релиз и не чистить вручную во время активной сборки. Подробности и синтаксис читать в [references/commands.md](references/commands.md) и `<MODKIT_ROOT>/PROJECTS_RU.md`; не пересобирать этот workflow вручную отдельными командами без причины.
- Для сравнения выпуска с предыдущей версией использовать `release upgrade-check OLD NEW`; глубокий `--deep-scripts` включать только когда нужен SCR round-trip. Для нескольких языков использовать `lang coverage/diff`, а не вручную сопоставлять DAT. Машинные отчёты при интеграции проверять через `schema validate`.
- Для первичного анализа запускать `audit --profile dev --json`.
- Для проверки коллекции передавать корень коллекции той же команде; ModKit сам обнаружит моды.
- Для DAT использовать только `dat`-команды. Сначала читать дерево или значение, затем писать в новый DAT и повторно запускать `dat validate` или релизный аудит.
- Для скриптов сначала выполнять `script audit-mod` и `script lint-runtime`; если исходника нет, восстанавливать его через `script decompile`, затем изменять RSON headless-командами и собирать через `script build`. Для доказательства различий двух бинарников использовать `script compare-scr`, а перед изменением persistent-массивов — `script compare-storage` старого и нового RSON. Если импорт непустого Lang.dat падает, изучить `lang_import.diagnostic`; продолжать с `--fallback-without-lang` только по явному решению, потому что диалоги не будут восстановлены. После такого fallback не собирать сырой вывод RScript как игровой Lang.dat: использовать `--lang-base` с проверенным прежним DAT либо сначала восстановить полноценные диалоги. `--lang *.txt` означает диагностический UTF-16LE-фрагмент, `--lang *.dat`/`--lang-dat` — проверенный игровой BlockPar.
- Для модульного скрипта использовать `script export-rsm`, `script validate-rsm` и `script build-rsm`. Перед rsmc ModKit сам создаёт Lang.txt/Lang.dat с узлом `Script/<ScriptName>`; SCR публикуется только после round-trip, runtime-lint и языкового аудита. RScript 4.15f является штатным и декомпилирует через настоящий CLI; 4.10f допустим только как явно обнаруженная legacy-версия и для RSON/SVR-конвертации.
- Для видимого `TDialogAnswer` использовать в RSON `DAnswer(CT('Script.<ScriptName>.<key>'));`, а обычную непустую подпись публиковать во всех `CFG/<язык>/Lang.dat`. `DATA/Script/Lang.dat` допустим как артефакт сборки/импорта RScript, но не доказывает загрузку текста игрой. Видимый литерал внутри `DAnswer(...)` и значения DAT, начинающиеся с `DAnswer`, `DText`, `CT` или `Format`, являются кодовыми заглушками. Управляющий `DAnswer('exit');` допустим. Соседний `*.lang.txt` только доказывает номера ключей и не копируется как игровой текст. Проверять цепочку командами каталога `script lint-runtime`/`script audit-mod`; без RSON ModKit доказывает лишь прямые `DAnswer(...CT("Script.<name>.<key>"))` из SCR. `DAdd/TDialogAnswer` не запрещать при корректном CFG; для `InjectAnswer` проверять целевой `TDialog` и его обработчик.
- В скриптах не сохранять сырые `Item`, `Planet`, `Star` или `Ship` в долгоживущем `TVar`/массиве: сохранять `Id(object)` и при миграции сначала обнулять старую ссылку. Для `Planet`/`Ship` использовать подтверждённые `IdToPlanet`/`IdToShip`. Не считать `IdToStar` встроенной функцией: звезду восстанавливать локальным ограниченным обходом `GalaxyStars()`/`GalaxyStar(i)` либо через сохранённую планету. Результат `GalaxyStar` отдельно проверять до `Star*`, `Id`, `RelationToRanger` и `Dist`; не передавать прямой `GalaxyStar(...)` в `Dist`. До `ShipStar(ship)` отдельно обработать посадку и доказать `ShipInNormalSpace(ship)` вместе с `!ShipIsTakeoff(ship)`; guard и объектный вызов разносить по операторам, не рассчитывая на короткое замыкание `&&`/`||`. `OrderTakeOff` и дальнейшие пространственные запросы разделять границей хода. Raw handle из `ShipGetBad` не разыменовывать: сначала сопоставить его с живым кораблём из текущей системы, а элемент `StarShips` перед `ShipIsTakeoff` дополнительно ограничить `ShipTypeN < t_RC`, исключая станции. Разгрузку и `ShipOut` также разделять границей хода. Никогда не выполнять `ShipOut` текущего `GroupShip` в прямом цикле с повторным `GroupCount`, даже с уменьшением индекса; использовать отдельный обратный проход и завершать обработчик после изменения группы. Persistent-массив инициализировать через `newarray(...)` на каждом нужном пути; новый массив мигрировать под отдельной версией хранилища, а не под уже пройденным first-run gate. После `newarray(1)`/`ArrayClear` начинать записи с `1`, пустоту проверять через `ArrayDim <= 1`, а парные persistent-массивы — на равенство размеров. Fixed persistent-массивы явно типизировать; прямое присваивание целого, float, строки, `CT` или `Format` уже достаточно, предварительный ноль не обязателен. Не включать `ArrayDim` как индекс; `N-1` для `newarray(N)` допустим. Предупреждение о terminal-слоте трактовать только как межходовой lifecycle-риск при чтении из другой функции Turn-графа, а не как общий запрет или требование всегда добавлять запас. В RSON держать не более четырёх `TGroup`, не обращаться из диалога к persistent-массиву, расположенному позднее handler, не помещать `<array[index]>`/`<cost>` в `TDialogMsg.Msg`, если индекс или значение рассчитывается только связанным handler: до `DChange` подготовить одну строковую переменную для `Msg` либо оставить `Msg` пустым и сформировать всю реплику одним `DText`. Не сочетать непустой `TDialogMsg.Msg` с `DText` в напрямую связанном handler: `DText` заменяет всю реплику и разметку. Не повторять локальные имена в разных ветвях одного RScript handler/function. Не передавать Item третьим аргументом `RndObject` и не менять `Order*`/`ShipSetBad` до проверки `ShipInHyperSpace`.
- У каждого `TGroup`, включая пустой и заполняемый позже через `ShipJoin`, требовать исходящие связи к `TPlanet` и `TState`. Одна связь не заменяет другую; неполный граф заставляет RScript 4.10f вернуться в Build без SCR.
- После `ShipPicksItem(ship, item, 1)` и ручного `GetItemFromStar → AddItemToShip` обязательно снимать тот же маркер через `ShipPicksItem(ship, item, 0)`. Обычный ванильный подбор через `ShipFreeFlight` без доказанного ручного переноса не считать ошибкой.
- Доказанному `t_Ranger` не назначать через `ShipOwner` специальные классы `5..7`; для временной стороны использовать `ShipStanding`/`NoTargetToShip`, сохраняя расового владельца `0..4`. После декомпиляции не оборачивать уже локализованные заглушки повторно: `CT(CT(...))` и `DAnswer(DAnswer(...))` являются ошибками, а `DAnswer(CT(...))` — штатной формой.
- Считать активный RScript частью SAV. Обычный аудит не предполагает наличие старого экземпляра; только при явном `script compare-scr OLD NEW` учитывать `runtime-saved-script-cache-update-shadow`, если SCR различаются, а `ScriptName` совпадает. Для несовместимого исправления применять новый runtime epoch/name и проверенную миграцию; хэш файла на диске не доказывает исполняемый код сохранения.
- Если `TState` достижим и от NPC, и от `AddPlayer=true`, отделять `CurShip == Player()` до любых setter/order/transfer-вызовов. В повторно вызываемом state-коде писать `ShipSetBad(CurShip, value)` только после явной проверки, что `ShipGetBad` меняется; посторонний флаг не является таким доказательством. Не открывать модальный `Dialog(...)` из фонового Turn-графа: в Turn ставить pending-флаг, а разговор показывать при пользовательском контакте. Не вызывать `TruceBetweenShips` из `TState` или достижимого helper, потому что функция синхронно запускает state-код обоих кораблей; для фоновой нормализации отдельно менять отношение и только действительно изменившийся `ShipBad`. Одноразовый диалоговый ответ и независимый путь отхода без связи с `TState` допустимы.
- Для пакетного `BuyPirate`/`BuyRanger`/`BuyTransport`/`BuyWarrior` в фоновом Turn не публиковать часть партии в общий `TVar`/`TGroup`, если более ранняя ветка того же графа обходит реестр и изменяет восстановленные корабли, пока ранний re-entry barrier не доказан. `runtime-batch-ship-spawn-partial-registry-reentry` учитывает helper-функции и предупреждает только при полном сочетании этих признаков. Не вводить общий список разрешённых вызовов после `Buy*`: одиночные `ShipFace`/`SetName`/`ShipSetCoords`/`ShipJoin` и последовательная пакетная настройка без обхода частичной партии допустимы; перенос настройки на следующий ход — защитный выбор конкретного мода, а не требование RScript.
- Перед `GetData(index, ship)` у мобильного корабля, восстановленного через `IdToShip`, отдельно отвергать `ShipIsTakeoff`, отдельно `ShipInHyperSpace`, затем доказывать посадку через `GetShipPlanet`/`GetShipRuins` либо `ShipInNormalSpace`; это устраняет очевидный ранний доступ, но не доказывает сохранность внутреннего script-data после перехода. Если ID свежего `Buy*` опубликован в persistent-реестр либо зарегистрированный корабль проходит `TransferShip`, а затем после `IdToShip` пересекает `OrderTakeOff`/`OrderJump`/`OrderLanding`/`TransferShip`, не использовать `GetData` даже за spatial-предикатом: `runtime-fresh-ship-script-data-cross-transition` требует вынести метаданные во внешнюю persistent-таблицу по слоту/ID. Обычный `GetData` без полного lifecycle, сам `IdToShip` и локальная настройка свежего `Buy*` допустимы; другие sinks расширять только после runtime-свидетельств.
- Для собственного литерала `CreateQuestItem('Type', owner)` из Lang `UselessItems` требовать точную непустую регистрацию `Bm/ItemsUseless/2Type_s` в CacheData. Префикс всегда `2`, суффикс `_s` обязателен для статической иконки, а локальный `DATA/ItemsUseless/2Type.gi` сам себя не регистрирует. Похожие `2Type`, `_c` или другой цифровой префикс считать нерабочими. Цель `_s` должна быть GI. Собственный путь `Mods\...\<Name>\...` проверять на наличие и декодирование; `DATA\...` считать пространством базовых PKG, а ссылку на другой мод разрешать без локальной копии только при соответствующем `Dependence`. Отсутствие изображения не считать падением игры: это warning с fallback `Usl_FishCont`. Для собственной предметной иконки предпочитать GI type 2 / три RLE-слоя и `convert png-gi --mode 2`; `runtime-quest-item-image-layout-atypical` считать предупреждением о малых карточках, а не запретом редкого подтверждённого формата. При сомнении смотреть `alpha_geometry` из `resource info/verify --json`, не объявляя художественную асимметрию ошибкой.
- Для видимого игрового текста предпочитать `от 80 до 100%`, `от 4 до 6 транспортов` и `этап 3 из 48` формам с типографским тире или числовым слэшем. Представимость символа в CP1251 не доказывает его наличие во всех bitmap-шрифтах SRHD. Не объявлять `%` и `/` запрещёнными: они есть в штатном Lang.dat; предупреждения `game-text-*` для пути, дроби или осознанного обозначения можно оставить либо точечно подавить.
- Только точное `ShipCustomFaction(..., 'SubFactionFixedStanding')` является безресурсным маркером. Для другого непустого литерала должна существовать штатная эмблема игры 2.1.2500 либо непустая регистрация `Data/Race/Emblem/2<фракция>` в Main.dat; вложенная запись `2SubFaction/Name` равнозначна `2SubFactionName`. Отдельный RSON даёт лишь предупреждение, поэтому перед сборкой проверять корень мода целиком.
- Для сложных маршрутов считать пользовательский helper с внутренним `GalaxyStars()` мировым обходом, а не `O(1)`. Плоский точный `S×S` допустим; сочетание двух мировых множителей с линейным поиском по растущему `ArrayDim(queue)` получает предупреждение о возможном `O(S³)`. Не объявлять его безусловной ошибкой без runtime-профиля; обычный релиз не блокируется, строгий режим может потребовать устранения.
- Для GI/PNG использовать нативные `convert gi-png` и `convert png-gi`; RangerTools и GUI не нужны. Для `DATA/ItemsUseless` явно выбирать `--mode 2`, если совместимость с предметными карточками не доказана иначе. Для остальных ресурсов использовать `resource info/list/verify/extract/build-gai/build-pkg`. В GAI точная запись кадра `(offset=0, size=0)`, вложенный GI `0×0` и `ZL01(GI)` являются поддерживаемыми вариантами, а не повреждением. Полностью пустая структурно корректная анимация получает `resource-empty-animation-placeholder` как warning; смешанные пустые позиции штатны. Не пытаться записывать HAI.
- Для текстового квеста сначала выполнять `quest info` и `quest validate`: изучать `location_images`, локации без кадров и `image_usage`. Для всего мода запускать release-аудит и проверять отдельные `quest-cards`, `quest-media`, регистрацию `Bm.PQI.*`, неиспользуемые ассеты и параметры `343x394 RGB`. Редактировать через `quest export-json`, собирать новым путём через `quest build`, затем выполнять `quest roundtrip`. TGE и GUI не нужны. Не объявлять визуальное постоянство персонажа или предмета доказанным статическим анализом.
- Для активного набора модов использовать `compat` с существующим ModCFG только для чтения. Интерпретировать `configured_order` как исходную позицию, а `order` как стабильный эффективный порядок по возрастанию `effective_priority`; отсутствующий Priority равен нулю, одинаковые значения сохраняют CurrentMod. `modcfg-priority-order-mismatch` означает, что игра может предложить перестановку, но ModKit файл не меняет. Даже при известном порядке не заменять `resolution: unknown` догадкой о результате сложного BlockPar/SCR/CacheData-наложения.
- Для публикации ZIP использовать `release check`, затем `release build`. Если мод должен лежать не прямо в `Mods`, обеим командам передавать точный одинаковый `--prefix`, например `OtherMods/MyMod`; он проверяет CacheData и задаёт корень ZIP. Для бинарного ZIP без исходников добавлять `--strip-sources`.
- Для прямой проверенной выкладки в игру или `Builds` сначала использовать `release plan` либо `release deploy --dry-run`, затем явный `release deploy <MOD> <DESTINATION_ROOT> --prefix OtherMods/MyMod --overwrite`. Deploy исключает исходники и project TOML, собирает соседний staging, сверяет SHA-256 и целиком заменяет старую папку без слияния; `ModCFG.txt` не меняется. Если откат не удался, сначала читать `doctor deployments`, затем по решению пользователя выполнять `release rollback`; `cleanup-transactions` без `--apply` только показывает план, а резерв не удаляется обычным `--apply`. Не считать низкоуровневый `pack` полноценной релизной проверкой.
- При подозрении на оставшиеся RScript/BlockParEditor сначала выполнять `doctor processes`; `--terminate` использовать только после просмотра отчёта.
- Если CLI недоступен, пользователь может завершить редактор по исходному имени EXE во вкладке «Подробности» Диспетчера задач; процесс не является защищённым или скрытым от системного списка.

## Интерпретировать отчёт честно

- Считать `failed` сбоем самой проверки, а не ошибкой мода.
- Считать `unsupported` неполным покрытием: сохранять файл побайтно, не объявлять его корректным или редактируемым.
- Считать `issues` контейнером ошибок, предупреждений и сведений; проверять `severity` каждого элемента.
- Учитывать, что профиль `dev` быстрый и неполный, а `release` декодирует все DAT и глубоко проверяет поддерживаемые ресурсы.
- Не называть победителя коллизии при `resolution: unknown`.
- Использовать `--allow CODE[:GLOB]` только для осознанного исключения с объяснением пользователю. Не скрывать поле `suppressed` из результата.

## Правила изменений

1. Сначала проверить состояние Git. Не перезаписывать и не откатывать посторонние пользовательские изменения.
2. Не редактировать установленные игровые файлы для диагностики. Создавать staging или рабочую копию вне каталога игры.
3. Не менять `Mods/ModCFG.txt`; `compat` и `modcfg` использовать только для чтения.
4. Не запускать `open`, не выставлять `SRHD_MODKIT_ALLOW_GUI=1`, не управлять ResEditor, RScript или BlockPar через видимый интерфейс.
5. Перед записью предпочитать новый output. Использовать `--overwrite` только когда пользователь явно разрешил замену или операция идёт во временной рабочей копии.
6. После изменения запускать ближайшую структурную проверку и затем `audit --profile release`.
7. Для релиза располагать ZIP вне дерева мода. Передавать пользователю ZIP вместе с внешними `*.manifest.json` и `*.audit.json`.
8. Использовать штатную адаптивную политику RScript: малый проект получает 60 секунд без подтверждённого прогресса и общий предел от 600 секунд, крупный — больше по размеру, объектам и строкам кода. Явный предел задавать только при доказанной необходимости; значение `0` отключает оба ограничения, но синтаксический preflight остаётся обязательным.
9. При неуспешной `script build --json` читать схему `srhd-modkit-script-build-v1`: `preflight_passed` не означает созданный SCR, это доказывает только `compiler_output_created`, а публикацию — `published_outputs`. Код `rscript-build-silent-main-window-stall` означает подтверждённый возврат RScript к главному окну Build без SCR и прогресса; обычный тайм-аут не переименовывать в этот код без оконного свидетельства.
10. Непроверенный результат декомпиляции сохранять только по отдельному явно названному `--keep-unverified`; не подменять им штатный output и игровой SCR.

## Границы гарантии

- Не обещать реальное runtime-поведение без запуска игры.
- Не обещать совместимость с сохранениями и любой комбинацией сторонних модов.
- Не считать SCR без RSON полностью семантически проверенным.
- Не считать структурный round-trip QM/QMM доказательством фактического прохождения квеста в игре.
- Не создавать writer HAI и не декодировать неизвестные VDO, CMAP, VO, MAP, OPT или RAW.
- Считать круговой проход GAI/PKG доказательством структуры, но не визуальной корректности в игре.
